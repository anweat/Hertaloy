system promot搭建：promot模板（角色+回复模板）+开发rules（包括可编辑文件范围）+初始化skill，排序按照历史/skill命中索引 ，添加时通过拖拽卡片添加进agent节点来组装。

skill：打标签，面向工程方向，具体技术点，/skill->从skill管理数据库中获取搜索，字典库模糊搜索。通过统一发现服务打包，获取后在promot压缩索引（按匹配，不全量），在之后调用直接上下文尾部补充，并落在agent.md。skill分级，全局/项目/回话，用于限定范围和小范围策略。做成卡片，

mcp 包装成promot中的列表（全量），通过/mcp获取具体信息（包括标签，可以补充相关方向mcp），可用状态和工具列表，（需要有测试可用性的脚本，不可用的不添加）按照添加列表加载，可以添加（上下文补尾）通过统一发现服务打包，做成卡片，

rules：开发规范和要求，先于skill，必须遵守，包含总体文件编辑范围（根部分）。做成卡片

promot skill mcp rules存储位置统一，需要时通过索引加载，不能直接通过文件调用，（可以通过数据库加密访问来防止）。

skill/mcp发现服务（内置容器）：来源为人或发现agent，可以包含md文档，rule文件，非二进制脚本（例如python）等，异步发现和调用，通过发现服务消息订阅来异步传递需要skill/mcp的agent，封装为容器（内含agent，可以多实例）以便于并行

plan：和普通的一样，有迭代要求，需要完成提交测试后再进行下一个部分，结束迭代前需要给明确调用结束，但是可以在中途因为设计模糊，冲突等原因暂停，之后修改重新索引。作为自定义状态机，暴露接口可以被查询到。由工作区sqlite管理

subagent：子代理受主代理完全控制，但是只能继承分化任务不能扩展职责（skill和mcp为主代理子集，需要由主代理编写plan和system promot（继承rules）），子代理上下文流式保存以便监控，可以由主代理中止，可以开多个（ui：主节点分化为“容器”包纳子节点实例，根据进度消化）

编辑文件范围：在根部分下的具体限定，作为建议，可以编辑，但是在编辑范围外的操作默认git临时存档，可删除存档，（和rule不同，rule规定根，这里限定具体范围，这里放宽权限是为了保证完成质量和可控分析）

来源：默认脚本通过 openai和anthropic兼容，再解析CLI harness路由，最后统一保存固定格式senssion用于分析。

tool 工具调用：有CLI harness的自动审核，默认接受，无CLI harness的封装tool和审批（参考pi？需要调研），接受更高的并行调用和工具结果返回等待以及订阅消息返回等待。，扩展tool可以支持以卡片形式拖拽入并纳入提示词

agent：含有mcp，skill ，promot，tool，rules等的对象，

harness：默认等同agent+session+上下文压缩（上下文管理），非CLI 的harness（原生）需要实现

session：会话，默认一次实例化创建一个，容量默认200k（根据模型来定义），有上下文压缩的默认还是单会话

上下文压缩：留余量自动调用总结轮总结后作为新上下文初始，也可通过外部模型总结辅助

character角色（agent模板）：作为封装好tool， promot ，skill，mcp，默认rules的完整智能体，含有默认标签（智能体层，skill，mcp的标签），便于自动化搭建时索引

容器：用于包含实例化对象，容器内实例的创建模板。标识可实例化部分，也就是需要有子级traceid作为索引，含有各种定义（子代理，skill发现服务等都是容器模板，作为定义），各个实例可以通过容器内模板自动创建（外部harness需要适配），区别于非容器部分

非容器部分：作为单例实例化部分，traceid只包含顶级索引名，不能被自动创建（当然不包括通过外部调用mcp创建画布时创建）

实例：可以自动创建，有完整生命周期，需要通过traceid来管理的相关对象，如subagent，子流程实例

消息队列：作为非直连agent间或者流程间传递信息的通道，通过订阅方式获取消息，默认检查和继承traceid子级。可以通过tool创建消息容器或者节点末尾策略发布消息，节点开头或者tool的容器含traceid的实例订阅消息

消息：需要实例化，通过tool等创建维护容器，默认包含消息队列id ，传递信息，traceid和是否需要回复消息（不需要回复时实例迅速消融），需要回复时需要限定回复消息结构，可以一对多多对一，各方都需要追加trace。多流程时需要发送方限定好各个成员然后依次传递和追加traceid。在最顶层有助手ai和人交互，这里也可以在消息队列发布消息，需要维护容器。

子流程：单个节点可以只包含编码好的命令行代码，脚本条件判断和并行/串行/异步/同步等运行策略（策略节点），可以包含agent节点或是封装好的character。用于简化重复步骤和封装步骤为工具，通过外层容器节点收纳，外层容器配置触发方式为：隧道（只含string标签的“隧道”类型消息）匹配主动调用（可以有多个入口，通过隧道的子项来进行分配，可以多参数，每次实例化）;维护消息队列订阅调用（单实例或者实例池）;工具调用/实例化/plan 等内部定义工具自动触发

主流程：单个画布（单个配置文件）上没有装在容器中的外层节点，每次启动时默认仅实例化一份并单独计算session（可以resume回调所有），工作流层级，可以包含agent节点，策略接待你，输入输出触发器（也就是可以被外部调用或者触发外部调用，可用于流程间响应），主流程一般只包含plan的模型，不包含具体实现的模型（防止上下文过多）

策略节点：用来获取输入信息后管理输出信息和输出规则的节点，默认可支持编辑json 1.逻辑部分：自定义的脚本语言，配置各个连接的节点（输入/输出/输入输出），节点代号(e.g. PIN_01)，节点返回消息范围（用于校验，可以正则，可以if？），支持调用工具（读，写，子流程等，基本和agent默认一致），然后储存到变量，进行运算分析，然后选择输出模式和策略(不一定需要全量输出，可以用于循环或跳出循环)。可以通过工具创建容器和实例用于消费  2。分配部分（可选）：agent代理用于分配任务，和前者一样，但不需要运算只需要有输入输出拼装。默认上下文需要给出足够多信息用于串联几者，创建规则后需要人为审批确认后加入promot用于严格自动化。

连接边：用于传输输出的json，agent节点定义好输出schema后（一般是继承输入后补充于尾部），输入获得全量json，然后根据json伺服器来选择和组装具体的输入信息json，边目前不支持边中分叉，支持一个节点多个边，每个端口最多一个伺服器，输入节点都需要使用伺服器处理，输出节点默认继承未经处理的全量输入多个就按顺序拼装后尾部补充输出，可以选择伺服器修改全量json

伺服器：有方向性，主要作为json操纵语言，需要有灵活的提取和选择以及拼装交互逻辑，输入为json，输出为多个string等变量，用于agent或逻辑节点中具体填入提示词或后续逻辑运算。

最顶层的助手ai：和人处于同一层，也就是可以支持画布的所有创建编辑，开始结束，日志查看，暂停，查看所有会话消息，查看消息队列等组件信息，和实时监控操作，定时触发检查的任务设置。其实就是间各功能封装mcp组装后提供出去的接口，然后将此助手也当作用户。

上下文管理：通过多层plan，多层容器来实例化多agent，尽量保证单个任务单个agent完成，尽量避免单个agent触发上下文压缩。

agent输出：需要是json格式，不符合可以重试，需要有自适应的输出字段要求补充到promot，应用时可以设计胶水agent转化输出节省上下文
