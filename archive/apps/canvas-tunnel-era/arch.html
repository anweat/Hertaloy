系统剖面

一个 TypeScript 的 agent 编排运行时。第一性是嵌套与生命周期 —— 容器就是实例，实例路径就是它的 id，历史只累积不覆盖。 这份文档画的是模块、动作与流程，供动前端之前先看清楚地形。

01六次归约

每一次都是把 N 套并存的机制证明成一套。这是整个设计的脊椎 —— 读下面任何一张图，如果某个东西看起来"本可以更简单"， 多半是因为它已经被压过一轮了。

#归约消掉了什么
1容器 is-a 实例slot / subscription / children / pool_cursor / overflow → 一棵实例树
2资产即变量卡片系统 + 四段上下文编译器 + 运行时预算裁剪 → 一套变量
3等待即锁callback / child / approval / 订阅 / PAUSED / 定时器 → 一张锁表（5 种 → 2 种）
4版本历史即状态策略节点 / 表达式语言 / 节点内 persistent / 内核时钟 → ObjectStore 的版本历史
5agent 就是一条命令行内核工具 / 工具桥 / 线协议 / backend 矩阵 → 端口 + 变量 + 沙箱外的 git
6状态只有两个形态WAL / 多种表 → 写一次的对象 + 一个可变头

第 4 次最省：节点内 persistent 与「等齐 N 条消息再原子消费」， 本质是在重新发明 ObjectStore 已有的东西 —— 版本历史 = 累加器 + 计数器 + 择优的候选集。plan@3 就是第三轮。

04一次执行

同步 handler 没有②。 它在一次事务里就提交完，没有可观测的 RUNNING 窗口。 这不是遗憾：在按长度画的图里，"有宽度 = 真的在外面跑"和"一个刻点 = 内核里一瞬间的事" 正好是要一眼看出来的区别。

05操作面

内核的授权表本来就是 (principal, scope, opclass)， 而 opclass 天然对应"改定义 / 改运行状态 / 只读"。 人和 AI 调的是同一组操作，差别只在那张表里 —— 界面不需要为 AI 另做一套。

类对象操作缺省
DDL
改定义		 模板 define_template validate_template 人有 · agent 无
DML
改运行状态		 实例 · 消息 create_run send_message spawn_child advance truncate_instance 人有 · agent 按授权
DQL
只读		 全部 get_status read_object list_versions explain_message 按 scope

决策只有一处。 授权判断全部收在 ControlPlane.check()， 放行与拒绝都落审计日志 —— 拒绝比放行更值得记， 它往往就是"权限配错了"的现场。操作可以留在自己那一层 （资源别名表住 state，内核够不着），但判断不能有第二处。

M1 那条值得单说：走内网还是走网关由端口声明决定，不由 handler 选。 所以沙箱工具里刻意没有 publish —— 给 agent 一个 publish 就等于让它挑传输方式， M1 会当场从结构性保证降级成口头约定。往带 tunnel 的端口 emit，它自然就走网关。
